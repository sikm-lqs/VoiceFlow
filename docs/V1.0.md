# VoiceFlow v1.0

产品版本 v1.0；Debian / Cargo / npm / Python 版本统一为 **1.0.0**。
目标平台：Ubuntu 24.04 amd64、Python 3.12、**X11 图形桌面**。
不声称支持原生 Wayland，也不自动安装本地 ASR 模型。

本次提交只纳入 v1.0 改动，安装包则保留工作区先前已有的录音/UI 未提交修复，
不回退现用行为。同目录附 `voiceflow_1.0.0_source.tar.gz`、
`voiceflow_1.0.0_build-info.json` 和校验文件；不能把此包称为纯净提交的逐字构建。

## 1. 一条命令安装 / 升级

在你自己的桌面终端执行：

```bash
sudo dpkg -i /home/sikm/Project/AI-Project/TTS/build/deb-package/voiceflow_1.0.0_amd64.deb
```

你这台机器的系统依赖已检查齐全。不需要再手动复制配置、合并 cleanup、
daemon-reload、enable 或 restart，也不用再次填写已有阿里云密钥。

新机器若缺系统依赖，推荐让 apt 同时解决：

```bash
sudo apt install ./voiceflow_1.0.0_amd64.deb
```

`dpkg -i` 本身不会下载缺失依赖；单命令并不意味着可以无视依赖或平台要求。
Python 扩展按 3.12 ABI 打包，包声明了对应 Pre-Depends。

### 自动发生的事情

```text
preinst
  ├─ 确定安装用户（优先 VOICEFLOW_INSTALL_USER，其次 SUDO_USER / PKEXEC_UID）
  ├─ 备份旧配置、服务、用户 drop-in、现用二进制和 Python 源码
  └─ 记录原有 enabled / active 状态；不先停掉正在工作的旧版本
dpkg unpack
  └─ 更新程序、包默认值、用户服务单元、登录助手
postinst
  ├─ 首次创建 /etc/voiceflow/config.yaml：迁移旧配置，或写入 {}
  ├─ 若个人配置已存在：原字节保留，不覆盖、不重写注释
  ├─ 检查合并后的配置（仅公共默认值与机器配置，不读取 root 的个人覆盖）
  └─ 以目标普通用户身份操作他的 systemd --user
       ├─ 首次安装：启用自启，有桌面环境则请求启动
       ├─ 原来 active：排队空闲重启
       ├─ 原来 disabled / masked：不擅自改为 enabled / unmask
       ├─ 原来 inactive：升级不强行启动
       └─ 无用户总线 / 无桌面 / 无明确安装用户：下次登录时完成
```

服务操作失败会报告 deferred，而不是谎报“已运行”。配置迁移失败会使
configure 阶段失败并保留备份；修复配置后可执行 `sudo dpkg --configure voiceflow`。
安装不会自动部署、启动或修改你的 vLLM 服务。

### 当前机器升级的边界

你现有 0.1.0 不提供录音状态协议，**首次升级请在没有按住 F10/F11、
没有识别中的时候执行**。旧版会被自动重启一次，但无法可靠判断它是否正在录音。

另一个历史边界：Debian 会先运行旧包的 prerm，再运行新包的 preinst。
新安装器只能记录 preinst 时观察到的服务状态，不能追溯旧脚本此前已经破坏的
状态；不能承诺修复任意旧安装器的副作用。v1.0 自己的 prerm 在 upgrade
时不操作服务，后续采用这套生命周期升级就不会再主动制造这种问题。
顺序依据：https://www.debian.org/doc/debian-policy/ch-maintainerscripts.html

从 v1.0 开始，后续采用本安装链路的升级会：

1. 由普通用户的临时 systemd 单元执行升级助手；
2. 设置短期升级门闩，暂时不接收新录音，已有录音继续完成；
3. 等待录音、ASR、清洗和 **Rust 粘贴完成确认**，再请求重启；
4. 最多等 180 秒。持续忙碌或状态不可用时不强杀，留待下次登录重试。

门闩带 PID/过期检查，助手异常退出不会永久禁用输入。多个升级助手用锁去重。
这不是对旧版本的追溯性保证，也不是操作系统级零竞态/零中断承诺。

### 非 sudo、SSH、无桌面

直接以 root 安装且无法确定桌面用户时，不猜测其他用户，也不启动 root GUI。
XDG 登录项在普通用户下初始化；升级时尊重该用户已有 disabled/masked 状态。
正常 sudo 安装会限定自动登录初始化的目标 UID，不会因全局 XDG 登录项
而自动启动其他账号的麦克风；其他用户主动点击菜单仍可手动启动。
管理员知道目标用户时也可以指定：

```bash
sudo env VOICEFLOW_INSTALL_USER=sikm dpkg -i ./voiceflow_1.0.0_amd64.deb
```

若没有活跃图形会话，安装成功仍不代表当前可以录音、捕获快捷键或粘贴，
需等 X11 登录。不会自动开启 linger 或更改系统登录策略。

## 2. 优化后的架构

```text
安装生命周期（root，只处理包和私密备份）
   └─ runuser + 最小化环境 → 指定普通用户的 systemd 管理器
                               │
XDG 桌面登录助手 ───────────────┤ 导入 DISPLAY / XAUTHORITY
                               │
                      voiceflow.service（用户级）
                               │
                voiceflow-session --run（拒绝 root）
                               │ 等待 X11 就绪；无图形会话退出 78
                    /usr/bin/voiceflow（Tauri / Rust / React）
                       ├─ F10/F11、悬浮窗、目标窗口
                       ├─ 剪贴板注入 / 恢复
                       └─ Python sidecar（JSON Lines）
                             ├─ 录音、pre-roll、60 秒上限
                             ├─ 本地 vLLM ASR → 失败后阿里云 ASR
                             ├─ 本地规则清洗（默认）
                             ├─ MiniMax（仅显式开启）
                             └─ 私密状态：录音 / 转写 / 粘贴 / idle
                                   ↑ Rust 发送 paste_complete
```

安装进程不转发 root 环境或 API key 到命令行。用户服务保留原有
`~/.config/systemd/user/voiceflow.service.d/`，由 systemd 继续加载凭证和机器覆盖。
登录助手与应用菜单入口都通过同一个用户服务启动，不再故意启动第二份应用。

运行时状态位于 `$XDG_RUNTIME_DIR/voiceflow/`，只包含版本、PID、状态和时间，
不记录语音、转写正文或密钥。新清洗模块也不记录正文/密钥。

## 3. 配置层级

优先级从低到高：

| 层 | 位置 | 用途 |
|---|---|---|
| 包默认值 | `/opt/voiceflow/defaults.yaml` | 随版本升级，不要直接编辑 |
| 机器配置 | `/etc/voiceflow/config.yaml` | 首次自动迁移；以后安装不覆盖 |
| 旧配置兜底 | `/opt/voiceflow/config.yaml` | 仅在机器配置不存在时使用，不与机器配置叠加 |
| 个人覆盖 | `$XDG_CONFIG_HOME/voiceflow/config.yaml`，默认 `~/.config/voiceflow/config.yaml` | 用户自行编辑，允许只写几个键 |
| 显式覆盖 | `VOICEFLOW_CONFIG` 指向的 YAML | 最高优先级文件层，仍为覆盖而非整份替换 |
| 清洗专用覆盖 | `VOICEFLOW_CLEANUP_MODE=off/rules/minimax` | 启动时覆盖文件中的清洗模式 |

映射递归合并，列表整体替换。缺失新字段使用默认值，
显式 `cleanup.enabled: false` 或 `mode: off` 都会保留。
**旧配置不含 cleanup 时，现在自动使用 rules；这与 0.1.1 的完全透传默认不同。**
如果你曾主动开启 MiniMax，安装器不会偷偷重置你的选择；默认值本身仍为 rules。

新文件采用运行时生成方式，不作为 dpkg 的个人配置载荷；每次升级只更新
defaults，而不是靠 `--force-confold` 解决冲突。历史 obsolete conffile 可能仍在
旧路径，但新机器配置存在时旧路径不再参与合并。

配置修改在下次启动读取，暂无热重载或清洗 UI 开关。
当前热键 F10/F11 由 Rust 固定注册；不要以为改 YAML hotkey 段就会改变热键。
`ux` 等历史字段也不代表都已提供独立可配置开关。

### 日常只需编辑个人覆盖

```bash
mkdir -p ~/.config/voiceflow
```

创建或编辑 `~/.config/voiceflow/config.yaml`，仅填写需要覆盖的内容：

```yaml
cleanup:
  enabled: true
  mode: rules
  fillers: ["呃", "嗯"]
```

关闭清洗：

```yaml
cleanup:
  enabled: false
```

改动之后运行（不用 sudo）：

```bash
systemctl --user restart voiceflow.service
```

## 4. ASR 与密钥

当前机器迁移后仍是：

```text
本地 Qwen3-ASR-1.7B
 POST http://127.0.0.1:8000/v1/audio/transcriptions
   ├─ 成功 → 清洗 → 粘贴
   ├─ 超时 / 被映射为不可用的错误 → qwen3-asr-flash 云端兜底
   └─ 正常但空语音 → 不调用云端
```

本地模型的实际名称/路径从旧配置原样迁移。全新安装默认模型名
`Qwen3-ASR-1.7B`，需与 vLLM 的 `--served-model-name` 一致：

```bash
vllm serve /path/to/model --served-model-name Qwen3-ASR-1.7B \
  --host 127.0.0.1 --port 8000
```

按需在个人 YAML 覆盖：

```yaml
asr:
  endpoint: http://127.0.0.1:8000
  model: /your/existing/served/model/name
  fallback:
    enabled: true
    model: qwen3-asr-flash
    api_key_env: DASHSCOPE_API_KEY
    enable_itn: true
```

**本地 ASR 不可用且未配置云端密钥时，应用不能凭空完成识别。**
安装包不包含密钥和模型权重。你当前已有密钥 drop-in，升级不用重新配置。

新机器可在用户的 systemd drop-in 中引用私密 EnvironmentFile；
创建/编辑 `~/.config/voiceflow/credentials.env`，权限设为 600：

```text
DASHSCOPE_API_KEY=你的密钥
```

创建/编辑 `~/.config/systemd/user/voiceflow.service.d/credentials.conf`：

```ini
[Service]
EnvironmentFile=%h/.config/voiceflow/credentials.env
```

随后 `systemctl --user daemon-reload`、`systemctl --user restart voiceflow.service`。
不要覆盖已有凭证文件，不要把真实密钥放入命令参数或仓库，也不要分享
`systemctl ... Environment` 等可能包含密钥的输出。

MiniMax 仅在 `cleanup.enabled: true` 且 `mode: minimax`（或环境覆盖）时使用，
从 `MINIMAX_API_KEY` 读取密钥。默认不会额外调用它；真实延迟与限制见 CLEANUP.md。
阿里云的 ITN 不等于去口水词，ASR system 上下文也不是通用清洗指令。

## 5. 使用与诊断

1. 登录 X11 桌面，聚焦要输入文字的应用。
2. **按住 F10 说话，松开识别并粘贴**；终端可用 F11 强制终端粘贴。
3. 明确独立的“嗯、呃”进行规则清洗；引用、代码、URL、路径尽量保护。
4. 单次录音上限 60 秒；原剪贴板按已有实现恢复。

查看状态与日志：

```bash
systemctl --user is-enabled voiceflow.service
systemctl --user status voiceflow.service --no-pager
journalctl --user -u voiceflow.service -n 40 --no-pager
dpkg-query -W -f='${Version}\n' voiceflow
```

不想自启：

```bash
systemctl --user disable --now voiceflow.service
```

之后升级不会擅自重新开启。希望恢复：

```bash
systemctl --user enable --now voiceflow.service
```

菜单中点击 VoiceFlow 是手动启动，不等于重新开启自启。不要用 sudo 运行程序。
若旧版正在录音、识别、粘贴，请等结束再手工 restart。

## 6. 备份、失败和验证范围

每次安装的备份在 `/var/lib/voiceflow/backups/<时间-随机ID>/`，
目录仅 root 可访问，含配置、用户 drop-in（可能含密钥）、旧服务和运行代码。
原二进制与 Python 模块也备份，但不重复复制全部第三方 python-libs；
恢复依赖请使用对应旧安装包。**不实现自动回滚**，不要把备份上传或公开。

`/var/lib/voiceflow/install-state.json` 记录最近的备份目录及处理结果，
不包含密钥正文。为避免误丢个人设置，本版 remove/purge 均保留运行时生成的
机器配置和私密备份；用户家目录中的配置和凭证也不会被卸载脚本删除。
完整清理这些数据应由管理员确认后手工执行。

有旧 deb 可先恢复对应版本，再从备份恢复旧路径下的配置、服务和程序。
旧程序不认识新的 `/etc/voiceflow/config.yaml`，不能仅降级 deb 就假设它已读到新配置。

验证区分两层：

- 自动测试使用假的用户总线/服务执行器，验证首次安装、enabled/disabled/masked、
  无桌面、重试、配置权限和敏感信息不输出等分支。
- 真实 dpkg 在 **fakeroot＋临时 DPKG_ROOT** 中测试全新安装、0.1.0 非 conffile
  升级和 0.1.1 conffile 升级，验证无交互迁移、配置保留及幂等配置脚本。
  旧包为无真实维护脚本的合成夹具：验证配置/载荷迁移，不代表已经执行了
  实际旧包维护脚本或真实桌面服务的完整升级。

因此不能把隔离测试描述成已经在你的真实会话完成升级。
